# 成功率下降：评测分布、评分与模型行为的区分

## 1. 下降的指标是什么

固定selection60开发任务，每题4次，总240次交互。主指标是成功轨迹数除以240，因各题试次数相同，也等于60题各自四次成功率的平均值。

Base 131/240=54.58%，1 epoch 121/240=50.42%，3 epoch 106/240=44.17%。不是“60题中有多少题至少成功一次”；后者pass@4分别是44/60、42/60、38/60。当前成绩不是final50。

1 epoch相对Base差值的任务配对95%区间跨0，不能据此证明稳定退化；3 epoch相对Base区间不跨0，但只覆盖当前任务和采样，不包含训练seed变化、任务家族相关性及评分语义争议。

## 2. selection60有什么分布限制

抽样是对1148个AReaL任务按固定seed哈希排序，前200训练、随后60开发、余888保留；没有按业务、条件分支、能力或语义家族分层。缺少预先指定目标业务分布，因此不能仅凭不均衡断言它偏离真实生产分布；可以确认它不是均衡能力测试。

参考动作涉及改航班33题、行李14题、取消12题、补偿8题、订票7题、乘客更新3题、转人工3题，标签可重叠。14种工具中参考涉及13种，缺list_all_airports。可合法不调用某工具，不能用调用频次当该项能力正确率。

60题来自4个初始DB快照，分别承载22、9、20、9题。共享DB不等于重复题，也不自动构成泄漏；但人物、订单和状态有相关性，不能当作60个完全独立场景。按同DB和写操作订单集合检查，HKEG34占7题，另有23LMN8和GCZ58I各2题；这只是可复核的相似性线索，尚非完整语义聚类。

|分组|Base|1 epoch|3 epoch|
|---|---:|---:|---:|
|HKEG34 7题，28次|16|7|8|
|其余53题，212次|115|114|98|

1 epoch的净损失10次有9次集中于该家族；3 epoch相对1 epoch，家族增加1次，其余任务减少16次。因此该分布放大了1 epoch的局部弱点，但不能解释全部3 epoch退化。这是描述性分解，不是删题理由或因果归因。

## 3. 评分与模拟用户确有问题

已严格回放证实：219的若干trial只有乘客数组顺序不同也判DB失败；923允许更晚五月返程但gold只接受一个日期；162允许保留一个重复订单但gold固定具体订单。用户模拟器在23/1自行要求额外改名，助手得到确认后执行，不能叫助手擅自更名。

新核对14任务发现：场景同时指定HAT084与8am–9pm，而DB中HAT084为04:00、gold选择HAT229。此任务本身有约束冲突；它也不能为模型把04:00读成16:00提供理由。

现有主分数主要衡量参考DB终态和预算内完成；过程合规与工具返回成功不是等价概念。相同验证器保证程序口径一致，不保证语义误判对三个模型抵消。已确认的问题数量来自抽查，不能估算一个可靠的“修正后成功率”，更不能把其余失败全归模型。

## 4. badcase已经能证明哪些模型行为问题

|样本|证据|反映的问题|
|---|---|---|

这些是具体行为证据，不等于每条reward=0的唯一原因，也不证明这些能力在总体上都比Base下降。最后一例已经正确查到profile和支付卡，进一步说明强制加一次查询不能解决全部问题。

## 5. 训练方面能确认与不能确认的事

能确认：100条训练对话中99条查profile，其中98条第一个工具就是profile查询，另1条先搜航班，没有先查订单再按需补profile的完整示范；评测里约一半对话先查订单。这是决策条件分布的明显缺口，不是工具名字没覆盖。

98条源SFT的正确性证据主要是源标签、规则和LLM判读；2条补充有真实执行和参考DB相等回执。judge已在评测案例中表现出漏判和误判，不能把机器审核通过直接视为无错误训练标签。

现有训练采用完整对话输入，仅批准的assistant输出计算loss；没有证据指向把system/user/tool全算loss或资料查询被全部mask。完整对话格式本身不是当前已定位的问题，不据此改成逐轮切片。

尚不能确认：过拟合、更新强度过大、源示范错误、模板分布差异分别贡献多少。3 epoch的学习率调度也不同于1 epoch。验证loss下降只说明拟合离线标签改善，不能替代在线交互能力。

## 6. 解决顺序（无卡可先完成前两类工作）

1. **建立可解释的评测v2候选。**保留旧分数；先在selection开发任务核查场景/DB/gold/policy一致性，定义合法终态接受集合、乘客顺序语义和模拟用户越界。任何改动先版本化，对三组同规则处理。仅终态判定修复可尝试离线重评分；改任务或模拟器必须三组重新交互，不能拿旧轨迹充新评测。
2. **把数据正确性和条件分布补齐。**先审100条完整示范，隔离确证错误和证据不足；从独立train任务补订单优先、支付偏好、多人多航段、退款/额度、合理拒绝和恢复。真实执行工具，不让LLM伪造返回；selection具体答案不进入训练。
3. **固定两层报告。**主报告为冻结分布下的任务成功率；辅助报告按业务、任务家族、五类能力给分母及错误证据。能力探针覆盖14工具与合法/非法边界，但不与主成功率混合，不为提高分数事后改变权重。未完全判读成功轨迹前，不公布全量五维能力正确率。
4. **再做一次有明确问题的新评测。**如果验证泛化，用隔离并冻结的独立确认集；如果验证评分修复，三模型在同一v2口径下比。换成final50本身不会修复训练分布或验证器问题，且不应消耗final来反复找修复方案。
5. **修复数据后从Base做短训练。**保持完整对话assistant-only，先1 epoch；学习率等参数在数据审计后定稿。当前不建议继续给同一100条增加epoch，也不把未达标SFT作为正式RL起点。

结论：已经证实评测语义问题和模型行为错误同时存在，训练数据还有明确条件覆盖缺口；目前无法给二者分配可信的责任百分比。优先修复可验证的具体问题，不能靠删掉难题、提高judge分数或简单加epoch解决。
