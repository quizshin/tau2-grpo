# A100 SFT 1 epoch 降分诊断与 3 epoch 后续实验

日期：2026-09-25。范围：离线读取原始轨迹、工具返回、评分明细、任务说明、训练数据及评分代码；未调用新的 LLM judge，未修改本轮评测分数。

## 结论

本轮没有达到超过 Base 的目标。最明确的可观察问题是：对「先给订单号、后补用户资料」的交互，SFT 更容易遗漏用户资料查询，把订单付款历史当作完整的可用付款方式，并受模拟用户后续偏移影响。模型也出现航班偏好解释、行李状态与收费计算错误。训练样本覆盖了工具名，但前置资料查询的位置高度单一；这是值得验证的数据分布问题，尚不能认定是唯一训练原因。

不能用这次结果证明 1 epoch 欠训练，也不能证明 3 epoch 会修复这些问题。数据分布、优化强度、模板和采样波动尚未分离。

## 1. 分数与配对

两个实验均为 selection60 × 4，完整 240 条，metrics_valid=true；已有 comparison 对记录的协议与哈希校验通过。Base 131/240=54.58%，新 SFT 121/240=50.42%，差 -4.17pp。按任务配对 bootstrap 的 95% 区间为 [-10.83,+2.08]pp，跨 0；不覆盖训练 seed 变化，相似任务之间也可能相关。

|配对结果|条数|
|---|---:|
|两者成功|99|
|两者失败|87|
|Base 成功，SFT 失败|32|
|Base 失败，SFT 成功|22|

相同 seed 不能保证两个策略走过相同对话：assistant 输出变化会改变用户模拟器上下文，后续 user 也会变化。配对用于定位差异，不是完全相同环境转移的因果实验。

## 2. 最强行为证据：缺少用户资料查询

|观测|Base|SFT|
|---|---:|---:|
|整个对话未调用 get_user_details|14/240|54/240|
|未查询资料且做了预订/改航班/改行李操作的对话|2|34|
|以 get_reservation_details 为首个工具|112|119|
|上述对话后来补查 get_user_details|99/112|67/119|
|全部 get_user_details 调用次数|227|188|

这里统计的是已发出工具调用，不把它自动等同于有用观察或政策合规。无需用户资料即可完成的操作也存在；54 条未查询不等于 54 条错误。32 条新失败中有 10 条完全没有查询用户资料。

具体证据（trial 从 0 开始）：

- **airline_23 / trial 3**：用户明确说 Visa 尾号 7447。SFT 未调用 get_user_details，却说个人资料只有旧卡 credit_card_1955700；用户随后接受旧卡，最终改航班用旧卡。目标是 credit_card_4421486。Base 对应轨迹成功。
- **airline_23 / trial 0**：用户指定 7447，SFT 仍用订单旧卡退款；用户指出后，SFT 声称看不到指定卡。这不是工具报错，而是未取得必要观察就做决定。
- **airline_1106 / trial 2**：航班和行李数可正确，但付款 ID 为旧卡，与用户多次指定及目标卡不同。
- **airline_14 / trial 0**：未取用户资料，混淆免费额度与已登记行李数，称当前已有 2 件免费行李，引导用户接受 4 件总行李和 2 件收费行李；原订单 total_baggages=0，任务要加 2 件，Gold/business 额度为 4 件。工具执行成功仍得到错误终态。

## 3. 工具错误率只是辅助信号

工具错误从 24/1586（1.51%）增至 39/1544（2.53%）。但 32 条新失败中只有 3 条含明确 error flag：airline_264/0、airline_755/2、airline_790/2，共 4 次错误。其余新失败大多是合法执行了不符合目标的参数/操作，或没有完成。

因此不能把净下降主要归因于工具 schema 报错。支付金额、缺库存、付款对象格式和禁止使用证书更新订单都值得修复，但其出现次数不是对成功率损失的因果分摊。

- 超上下文：Base 1 条，SFT 4 条。新失败配对中只有 airline_698/1、airline_802/0 两条是超长终止。
- max_steps：Base 26 条，SFT 21 条，整体没有增加。新失败配对中有 3 条达步数上限。
- 平均 assistant 消息数 11.13→11.14；assistant 已记录 completion tokens 601,618→453,127。因此不是整体输出更长导致的普遍退化。
- 多工具 assistant 消息 170→223。没有据此发现“多工具不能执行”的证据，不应退回单工具来掩盖问题。

## 4. 用户模拟器与严格评分的影响

以下结果仍保留官方失败分，不事后扣除、不重算“修正后成功率”。这些案例说明分数变化不能全解释成模型核心能力变化。

- **airline_219 / trial 2：乘客列表顺序。**目标是 [Nora,Ethan,Liam]，实际是 [Nora,Liam,Ethan]，人员及 DOB 相同，唯一写操作为该乘客更新。db_check=false。评分代码哈希 JSON 时只排序对象 key，保留列表顺序，因此该用例对顺序敏感。业务语义基本相同仍会失败。
- **airline_23 / trial 1：用户偏离原目标。**模拟用户看到账户名与乘客名不同后，主动要求把 Amelia 改为 Mia；SFT 执行了额外乘客修改。原任务仅改日期和行李，这个额外写入使最终状态不符。不能把它简单标为“模型擅自改名”，因为实际对话中用户提出并确认了要求。
- **airline_923 / trial 1：返回日期漂移。**模拟用户明确提出 May 24，模型按其指示执行；目标动作是 May 25。需要把 task instructions、用户生成内容与 gold 三者一致性单列审计。
- **airline_162 / trial 1：保留哪张重复订单。**模拟用户选择保留商务舱 6DC4D8，模型按确认取消另外两张；gold 要保留 90A522。该任务说明仅要求保留一张、取消重复项，存在目标选择与交互选择冲突。
- **airline_691 / trial 2：双方共同偏移。**模型先正确列出 11:00/14:00 在 8–21 点内，随后又错误称不在窗口；模拟用户接着要求窗口外 04:00 的 HAT084。这是模型错误引导与模拟器偏移叠加，不能单归模拟器。

## 5. 训练数据质量与分布

100 条训练完整对话中：98 条 AReaL 来源、2 条已有执行回执的补充。数据通过源标签、规则和 LLM 审核，不等于全量官方环境重放验证。

关键新发现：99 条含 get_user_details；其中 **98 条第一个工具就是 get_user_details，另 1 条先 search_direct_flight；0 条是先 get_reservation_details、再 get_user_details**。评测中约一半对话以订单查询开始，资料需要在中途补查。训练教了资料查询，但几乎只教固定开场位置，没有覆盖此次退化最集中的条件分支。

对现有监督的核对：

- get_user_details 101 次全部被纳入 approved assistant loss。
- 103 次预订/改航班/改行李调用之前均已出现用户资料查询。
- 各类工具调用均有监督，不是把工具输出当标签，也没有把资料查询全部 mask 掉。
- 14 种工具都出现并不代表关键依赖、支付偏好、退款卡选择、条件分支得到均衡覆盖。
- calculate 只有 1 次、search_onestop_flight 4 次、send_certificate 2 次；更重要的是这些工具在何种上下文下执行，而不是为了数量机械补齐。

训练前后离线验证 loss 0.46134→0.34055。留出集来自相近的源数据分布；这个结果证明对参考标签拟合改善，不能证明交互分布覆盖足够。现有证据没有证明“过拟合”，也没有证明“仅欠训练”。完整对话格式本身尚未被定位为因果，不据此切换成决策轮拆分。

## 6. 下一步优先级

1. 完成已授权的同数据 3 epoch 实验，回答增加训练量在当前数据下是否有帮助。固定现有评测协议，不中途修改 prompt、用户模拟器、上下文上限和评分。
2. 下一版数据优先增加训练池里的「先订单后资料」完整交互、从卡尾号定位 payment_id、改签与取消退款规则区分、用户纠错后重新查证，而不是继续大量复制“开场先查资料”模板。
3. 增加工具执行后的核验与恢复：行李总量/免费额度、航班时间窗口/偏好、余额/证书适用范围、缺库存后换有效航班。数据依然来自 RL train 范围；selection 的具体任务/金标准不进入训练。
4. 独立审计用户模拟器与 gold 冲突、乘客列表顺序等评分敏感性。任何修订形成新的协议版本，并让 Base/SFT 在相同新协议下对比；不回填或美化本轮成绩。
5. 3 epoch 即使变好，也需看同任务族、错误类型及置信区间；单次 seed 的涨分仍不能称为稳定提升。

## 7. 已启动的 3 epoch 实验

- 运行：results/runs/sft_staged_v2_A100_ep3/seed42。
- 起点：同一个 Qwen3.5-4B Base；同一冻结 A100 数据，完整对话、approved assistant-only loss。
- LoRA r16、lr3e-5、batch1×accum8、seed42；3 epoch，预期39次更新；保留3个epoch检查点，最终评测epoch3。
- 这是从 Base 重新训练的3轮配方。Cosine 学习率按3轮衰减，不能把第1轮视为先前1轮配方的完全相同检查点。
- SwanLab run ID r2599bdc。
- 训练 GPU0；完成后 CPU 合并，再 GPU0 policy + GPU1 user 跑 selection60×4。
- 预计训练约2小时，评测45–70分钟；硬上限训练3小时、评测3小时，总9 A800 GPU小时。用户已明确授权此实验。
- 恢复每10分钟监控；仅异常/需操作/完成通知。
- 接续控制器支持参数化epoch/step校验；tokenizer语义一致后恢复Base原文件，保存转换前文件与哈希回执。模拟器使用现有Python模块入口，避免缺失vllm可执行文件。
- 远程CPU相关测试11个通过；真实训练启动并完成训练前52条离线验证，进入0/39更新。未宣称3轮训练或评测已完成。
