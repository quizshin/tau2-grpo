# 4B SFT：从 SwanLab 曲线到失败轨迹

简历中的成绩是预期目标。本报告只使用当前4B实测证据，不推算9B结果，不提前填入RL提升。当前先完成SFT分析，RL方法比较留到下一阶段。

## 1. 先确认读的是哪个实验

SwanLab：[SFT-Qwen3.5-4B-lora16-lr1e-4-5ep-seed42-20260909](https://swanlab.cn/@quizshin/tau3-grpo-pytrio/runs/vr3e6ezj/chart)。2026-09-11已实际打开网页并查看训练与验证图像；同项目另有4B历史实验，不能混用。

原始配置：Qwen3.5-4B，LoRA r16/alpha32，lr1e-4，45/5完整对话，5epoch，30次更新。训练目标是预测参考对话中的assistant输出（含工具调用），用户及工具返回作为上下文。SFT期间不调用用户模拟器。

## 2. 按顺序读四张图

### train/loss：先看趋势，再看波动

含义：每次记录的训练批次上，对正确目标token预测的交叉熵损失。越低代表对参考输出预测更有把握，不是错误率。

首步0.505151，第二步0.623510，末步0.247658。曲线有锯齿但总体下降；各批对话难度和长度不同，不要求每一步都下降。训练全程汇总train/train_loss=0.331699，和末步train/loss不是同一指标。

学习方法：先检查是否有限、是否持续异常升高，再问局部峰值是否对应长/难样本。没有逐批难度归因证据时，只能说波动可能与批次组成有关，不能直接认定是哪条数据造成。

### val/loss：检查未参与梯度更新的参考对话

| step | val loss | 怎样理解 |
|---:|---:|---|
| 0 | 0.557704 | 训练前基线 |
| 6 | 0.399761 | 第一轮改善明显 |
| 12 | 0.363127 | 继续改善 |
| 18 | 0.357469 | 收益减小 |
| 24 | 0.354217 | 最佳 |
| 30，恢复最佳前 | 0.354258 | 基本进入平台 |
| 30，恢复step24后重测 | 0.354217 | 是恢复验证，不是另一次训练收益 |

SwanLab横轴写30不代表每个点都来自第30步权重：原始日志在step30记录了末步评估和恢复最佳后的评估。分析细微差别时必须看事件身份。最佳检查点是step24。

从0.557704到0.354217约下降36.5%。这表示验证参考输出的预测损失下降，不能写成“成功率提高36.5%”。只有5条验证对话，不能凭这个曲线证明广泛泛化；最后0.000041的反弹也不足以宣布明显过拟合。

### train/lr：先排除预设调度的影响

记录从0、5e-5、1e-4逐渐衰减，末步约3.14e-7，符合warmup＋cosine调度。曲线下降是预设训练策略，不是模型效果指标。学习率变小也可能让后期loss趋平，不能仅凭平台期断言数据已经完全学透。

### train/grad_norm：检查有没有正常学习信号

记录范围0.230236–1.319746，均有限且非零，没有从图中观察到梯度爆炸或整段全零。不要用梯度大小给能力排名，也不要仅因某点大于裁剪阈值1就认定裁剪失效：日志可能记录裁剪前范数。

本阶段结论：SFT训练数值表现正常，最佳权重恢复有历史逐张量审计，参考对话预测改善。但模型自主执行任务的能力需要看真实生成。

## 3. badcase从哪里来，能说明什么

SFT run里的dataset样例是参考答案，不是模型生成。当前没有独立4B SFT selection生成评测，不能凭空列出该测试集的失败。

可用的真实证据是RL-009 **第一次RL更新之前**的8条采样：使用SFT-003合并模型，新RL适配器初始B为零，尚未发生RL学习；启动核验和初始权重审计支持其SFT初始化身份。日志保存在RL目录，但生成发生在第一次更新之前，上传显示step1不代表由step1更新后的权重生成。

因此命名为“SFT初始化模型的预更新诊断”，不是独立评测。用户模拟器为27B INT4；任务来自训练任务集，仅2个任务各4条。

| 任务 | 成功 | 失败 | 失败标签 |
|---|---:|---:|---|
| airline_709 | 3/4 | 1/4 | wrong_outcome |
| airline_1072 | 3/4 | 1/4 | turn_limit |
| 合计 | 6/8 | 2/8 | 仅诊断样本 |

不能把6/8当作正式SFT pass@1，也不能由仅2条失败估计总体错误类型分布。

## 4. Badcase 1：查到了、算对了，但没有执行

身份：airline_709，原始第1条，reservation=4FDFNE。7个助手轮次、3次执行工具调用。score=0，scored=true，DB=0，COMMUNICATE=1。

| 顺序 | 已发生的动作/证据 | 分析 |
|---|---|---|
| 1 | 用户要求经济舱升商务舱 | 任务需要修改订单状态 |
| 2 | get_reservation_details：经济舱票价139 | 查到当前订单 |
| 3 | get_user_details：读取付款方式 | 支付信息准备 |
| 4 | search_direct_flight：该航班商务舱430 | 差价430−139=291，模型算对 |
| 5 | 用户明确同意，选择尾号2090信用卡 | 已具备进入修改步骤的条件 |
| 6 | 助手称“I've processed the cabin upgrade”“charge of $291 has been applied” | 没有update_reservation_flights调用，属于无执行依据的完成声明 |
| 7 | 用户接受、结束 | 用户满意不能代替真实任务完成 |

初始和最终DB hash完全一致，独立于自然语言说辞；全部3个调用都是读取工具。失败重点是“确认后未调用修改工具”，不是数学错误，也不是工具API报错。

正确的下一步是按已确认的订单、航班、舱位与支付方式调用修改工具，核对成功返回，再报告完成。改进假设：检查SFT数据是否足够覆盖“确认→写工具→检查结果→总结”，增加同类完整成功示范；若要使用失败样本，先修订为正确轨迹，不能把原失败输出直接当SFT标签。

[完整输入与生成轨迹](../results/analysis/sft4b_learning_20260911/case_1_airline_709.md)。

## 5. Badcase 2：重复查询、读错字段、迟到的执行

身份：airline_1072，原始第5条，reservation=9XZ6MK。15个助手轮次，9次已执行工具调用；score=0，scored=false，termination=max_steps，failure=turn_limit。

| 过程 | 直接证据 | 分析 |
|---|---|---|
| 开始 | 一次生成get_reservation_details和get_user_details，但只收到前者返回 | 当时max_parallel_calls=1；执行实现只取前N个调用，存在运行协议影响 |
| 前半段 | get_reservation_details共出现5次 | 多次重复读取未推进任务；不能把所有重复的根因只归给模型 |
| 查询票价 | 去程basic经济舱73，回程65 | 对照工具返回是核查事实的依据 |
| 模型解释 | 把去程说成65；把economy余座0解释成票价0且可购买 | 有明确的数值/字段理解错误 |
| 模型报价 | 两人260、退款6604 | 正确票价(73+65)×2=276，原支付6864，价差6588；这里按展示的票价与支付记录核对 |
| 收尾 | 多轮讨论退款方式、再次确认，最后才调用update_reservation_flights | 最后工具返回已降为basic_economy，退款记录−6588 |
| 终止 | 达到15轮预算，未正常收尾评分 | 不能称“完全没执行”或“官方DB评分失败”：这条没有终局评分结果 |

模型说错的退款额比实际多16美元。最后工具参数使用了正确73/65，说明自然语言解释与实际操作也可能不一致。

学习方法：分开标记三件事——可确认的模型错误（票价/字段）、配置影响（第二个调用未执行）、终止机制（max_steps导致零分）。不能因为reward=0，就把这三件事合成一个“模型能力不足”。

改进顺序：先核实并修正多工具调用处理协议，再评估减少重复查询/确认是否改善效率；单纯提高轮数可以诊断预算影响，但不算修复读错价格。若改变轮数，需与旧预算分开报告。

[完整输入与生成轨迹](../results/analysis/sft4b_learning_20260911/case_5_airline_1072.md)。

## 6. 学会自己做一条轨迹的分析

依次填写：用户目标→必须改变的状态→助手实际工具调用→工具返回事实→助手口头声明→终止原因→奖励是否真的完成评分→直接证据→原因假设→验证方法。

本次两条示例最值得记住：第一条“回复成功但状态没变”；第二条“状态已变但超时未完成评分，而且报价有错”。相同的零奖励，可以对应完全不同的问题。

下一步SFT完整评估需在独立selection任务上冻结模型、模拟器和预算，生成新轨迹，分别统计任务成功率、工具错误、虚假完成、事实错误、重复调用与超时。当前无卡阶段只完成已有证据分析，没有冒充执行新增GPU测试。RL分析后续沿用这个方法，再增加奖励优势、过滤和GiGPO等训练指标。
