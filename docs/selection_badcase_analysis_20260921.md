# 四模型 selection badcase：为什么没有看到净提点

日期：2026-09-21。范围：已完成的 Base / SFT new-off / GRPO E0 step20 / MT-GTPO reference_write/v3 DF off step20。本次只读原始轨迹、CPU重放和统计；未新采样、未训练、未改奖励或官方分数。本文不是后续 paper_env_split_v4 的效果报告。

## 1. 结论与证据边界

本轮没有观察到净提点：GRPO相对SFT少成功9条，MT相对GRPO再少4条。失分主要表现为**对话正常结束，但写入的业务状态不符合目标**，不是新增执行异常，也不是预算终止大幅增加。优先研究“写操作业务参数与最终目标状态的一致性”。

不能据此说算法已经被证明无效。GRPO−SFT为−3.75pp，95%任务配对bootstrap区间[−11.25,+3.33]；MT−GRPO为−1.67pp，区间[−8.33,+5.00]，都跨0。只有一个训练seed、60个selection任务；固定trial seed也不意味着不同模型经历完全相同的模拟用户对话。下述同task/trial得失是描述性对比，不是固定对话的因果实验。

历史独立评测GRPO47.5%与SFT43.75%也未给出明确正收益（差值区间跨0），而且历史策略/用户温度0.4/1.0与本轮0.7/0.7不同，不应合并。历史训练策略/用户为1.0/0.0、训练内验证策略0.4，协议差异可能影响表现，但本次没有温度消融，不能把失分归因于温度。

## 3. 失分来自哪里

|模型|成功/240|官方已评分但失败|预算终止|预算结束时DB已达目标|
|---|---:|---:|---:|---:|
|Base|120|95|25|3|
|SFT|108|107|25|7|
|GRPO|99|115|26|3|
|MT-GTPO|95|123|22|4|

440条官方失败都是DB=0、COMMUNICATE=1；本任务没有额外communicate断言，因此COMMUNICATE=1不能解读为模型已满足全部用户需求。98条预算失败另计。四组执行异常均0。

- SFT→GRPO：同task/trial下**补回27条、丢掉36条**，净−9；总数拆解为官方失败增加8条、预算增加1条。
- GRPO→MT：**补回29条、丢掉33条**，净−4；官方失败增加8条，预算反而减少4条。
- SFT/GRPO/MT官方失败里，DB完全未变且未达标分别33/20/45条；改过DB但从未达标68/88/72条；曾达标后又偏离6/7/6条。GRPO更经常实际做了修改，但不一定改对；MT也存在没有完成必要写入的失败。
- 预算终止中共17条最终DB已经达标，说明收尾效率仍有改进空间；它不能解释全部失分，也不能据此把这些轨迹直接改判成功。

**支付、航班与写操作约束值得优先看。** GRPO的36条对SFT失分中，32条存在支付/金额/历史/补偿字段差异，13条有航班字段差异，14条仅有支付或补偿字段差异。MT的33条对GRPO失分中，对应为28条、12条、6条，另有7条涉及舱位。这些类别重叠；选错舱位会连带改变票价与付款金额，不能把支付字段差异直接当成32次选错银行卡。

## 5. 历史训练为什么可能未补上这些短板

### GRPO：终局信号稀疏，无法告诉模型哪次写入出错

复用已审计的1,280条GRPO训练记录：160个8轨迹组里，48组全失败、15组全成功，合计**63/160=39.38%**的组终局奖励完全相同，对应504条轨迹没有组内终局优势差异。实现是`(score−group_mean)/(group_std+epsilon)`；这些组的终局策略梯度信号为0，KL项仍可能更新，不能称作完全未训练。其余97组有区分信号，但终局0/1仍无法直接指出“航班对了、付款卡错了”。

前后四个5步区间成功数120/130/130/136（各320候选）并非毫无进步；训练内selection却从step10的118/240变为step20的114/240。任务调度会影响训练成功率，不能把区间变化当学习曲线的严格因果证据；但继续多跑步数也没有现成依据。GRPO梯度非零，KL loss从step1的0.0101到step20的0.1299，不支持“没有发生更新”的解释。

### MT-v3：过程上做对过，不等于最终任务做对

重新读取20份实际训练buffer，全部与既有清单逐文件hash一致（借用v4审计的来源清单，仅验证文件身份；分析对象仍为reference_write/v3训练）。

- 有正过程奖励的轨迹中，455条成功、124条官方失败、119条预算失败。部分做对而最终失败本身正常，不能仅凭这个比例认定奖励错误。
- 更具体地，**25条官方失败轨迹拿满了+1的正工具奖励额度**；其中**12条还执行了奖励为0的非参考写操作**，包括额外取消、额外修改乘客、发证书等。全量条目与操作参数已保存。
- reference_write/v3实现对成功匹配的参考写入支付过程奖励；其他非报错的替代写入保持中性。于是“完成参考动作后，又写坏结果”的惩罚主要依赖最终失败信号，过程分不会自动撤回之前已获得的奖励。
- 这里的+1是正**工具调用**奖励总和；轮内同时有负奖励时，净轮奖励不同。不能推断这些轨迹的联合优势必为正，更不能说模型有意钻奖励空子。
- MT训练内selection从step10的118/240到step20的104/240，KL loss从0.00364到0.29580，提示应关注更新偏移与泛化；没有检查点消融/多seed证据，不能直接宣布过拟合或归因于KL系数。

## 6. 当时的初步建议（已由后续信号审计调整）

建议从原GRPO出发，验证**写操作反馈是否与业务参数正确性及最终状态保持一致**。先在现有train50历史buffer上定义和离线审计这一项反馈：必须区分依据充分的正确写入、合法替代、错误参数及破坏已完成状态，尤其是支付对象绑定与额外写入。应使用实际生效参数/DB变化，而不是简单比对参数字符串；不得给策略看到selection参考答案，也不把本次60题作为新增训练样本。

只有这项离线规则及争议标签可解释后，才提出“原GRPO vs GRPO+该单因素反馈”的有界GPU对照，保持初始化、任务调度、采样/评测条件、预算等一致。暂不同时改温度、上下文、KL或多个算法；不能保证这项一定提点，实验目的就是检验上述假设。本次仅完成诊断与证据留存，未修改奖励或启动实验。
