# 直接语义比较 v1：远程实现与独立任务盲测

2026-09-16。本轮离线实验完成，未接入 RL、未启动 GPU 训练。直接比较能给出更多判定，但新任务上出现双向一致的误合并，当前候选不能作为 RL 语义分组依据。

## 1. 实现范围

新增 `tau3_grpo/analysis/audit_semantic_pairs.py` 与 `score_semantic_pairs.py`，配置为 `configs/analysis/semantic_pair_direct_v1_20260916.json`，提示词为 `configs/prompts/semantic_pair_direct_v1.txt`。原有 v4 状态提取器和训练入口未因本轮实验修改。

比较器读取完整可见历史，排除奖励和隐藏字段。先检查同一 comparison_group、任务、policy、数据库以及已观察工具证据；不一致的对由本地规则分开。通过过滤的对分别请求 A/B、B/A，两向输出均有效且一致才接受，否则弃权。模型为 GLM-5.3-Flash，temperature=0、max_tokens=8192、timeout=180 秒、并发 4；请求前核验输入与整轮预算。

最终证据协议把正文按换行和最长 600 字符切成不丢字符的片段，模型引用 `A:m14:s0` 等编号，本地再解析成原文及位置。明确判定必须引用双方原文；merge 必须有共同状态且无差异，separate 必须列出差异。引用存在只能证明出处有效，不能证明推理正确或覆盖全部重要差异。

API 输入只包含冻结的无标签配对和可见历史，不传 expected/category/reason。原始响应、方向判定、引用、哈希和调用成本均保存。分组审计要求组内每一对都双向 merge，不使用传递闭包；满足这一条件也仅是候选组。

| 开发版本 | 配对结果 | 请求数 | 报告 token 数 | 请求耗时之和 |
| --- | --- | --- | --- | --- |

逐字引用版本因模型省略正文、改写弯引号或换行触发 `unsupported_pair_quote`。之后明确修订为证据编号协议；保留初次输出与源码，未将修订后的调用当作原版本重试。第二行包括 1 对规则过滤、1 对工具调用 ID 不变性和 3 对实质语义比较。

远程最终相关回归为 **54 passed in 1.60s**，覆盖比较器、评分器与现有 API 接口。初期有一条测试把提示词中的 “No rewards” 误判为泄漏，修正为只检查可见历史载荷；这是测试断言修正，非运行实现修正。首次开发 API 运行在发现该测试失败前已启动，原始测试日志保留。

同一开发配对上 v4 为 1 对 ID 不变性通过、4 对实质关系弃权，直接比较最终为 5/5。下述盲测使用不同任务，未重跑 v4，不能据此比较两种方案的总体准确率。

## 4. 盲测结果

| 类别 | 已标注对数 | 正确 | 误合并 | 弃权 |
| --- | ---: | ---: | ---: | ---: |
| 本地工具证据过滤 | 17 | 17 | 0 | 0 |
| 工具调用 ID 不变性 | 3 | 3 | 0 | 0 |
| **实质语义模型比较** | **10** | **4** | **4** | **2** |
| 全部已标注 | 30 | 24 | 4 | 2 |

另外 6 对 unresolved 保留原始输出，不在上表评分。17 对过滤和 3 对 ID 检查不能用于证明语义泛化；不能只报告总体 24/30。

实质语义部分：3 对等价关系全部正确；1 对支付选择不同正确分开；6 对告知内容/承诺不同的负例中，4 对误合并、2 对弃权。误合并集中在 airline_293 step6，同一任务内相关性很强；虽不足以估计普遍错误率，但足以否定当前候选可直接使用。

| 误合并 pair ID | 输入中的关键差异 |
| --- | --- |
| `293_s6_02` | trial0 确认航班为 `7L3NQJ4`，trial2 为 `7L3NQJ` |
| `293_s6_03` | trial0 确认航班为 `7L3NQJ4`，trial3 为 `7L3NQJ` |
| `293_s6_13` | trial1 未明确提供取消原因，trial3 明确 change of plans；航班编号告知和退款时间告知也不同 |
| `293_s6_23` | trial2 告知退款在 5–7 个工作日内到账，trial3 未告知到账时间 |

四对都双向 merge。模型倾向于认为订单、数据库事实和下一步取消操作相同就足以合并，忽略已经向用户告知并获得确认的内容差异。提示词已经要求保留这些差异，所以不能仅靠再加一句提醒认定问题解决。不能用数据库中的正确航班号替换历史中实际告知的航班号。

`293_s6_01`、`293_s6_12` 因双向不一致弃权；另 3 对 unresolved 也双向不一致，共 5 对。实质负例 `466_s6_12` 正确分开：一方已选择 Mastercard 7230 支付并询问退款路径，另一方尚未选择支付方式。全部引用校验通过仍未阻止误合并。

7 个最大候选合并组中：2 个含明确错误边，2 个含 unresolved 边，1 个仅工具调用 ID 不变性，2 个为已标注实质正例。没有“两条 merge 加一条 separate”的三角形，不代表分组正确；完整且双向一致的组仍可系统性误合并。详见运行目录中的 `manual_review.json`。

## 6. 后续建议，尚未实现

保留直接比较器作为离线审查工具，暂不作为 RL 最终合并判据。下一版可验证“关键约束与承诺逐项比较”的混合方案：固定检查订单/航班标识、日期、金额、支付及退款去向、到账承诺、取消原因、用户授权范围及待答条件，每项保存双方原文；缺失、冲突、仅由数据库推定的值分别表示，不默认等价。

这些字段需允许表达多对象、多次修订和确认所针对的具体提案，不能退回只填几个最终槽位就丢失历史关系。模型负责解释措辞，程序核验引用、显式值冲突及确认范围；未覆盖或无法确认的语义保守弃权。即便逐项一致也只是可检验的候选条件，不保证天然正确。

先将本轮反例作为开发回归，再在新的、未阅读任务上冻结评估，重点考察同一下一步动作但承诺/授权不同的负例，同时保留真正等价正例检查覆盖率。本轮所有已读任务此后均按开发材料管理；不得修后重跑同一批并称作新盲测。只有离线误合并受控，再验证真实 RL 组中的覆盖、成本和 step advantage；本轮不提供 RL 收益结论。
