# 假设语义模型下的目标、条件与确认范围归并（2026-09-14）

按本轮要求，**假设已有语义模型，不调用真实模型**。已完成从模型结构化输出，经证据校验、状态更新、归并到 GiGPO 步级优势的离线链路。这里验证的是后端逻辑；真实模型是否能稳定给出这些语义，仍未验证。未更改默认 v1，未连接线上 RL hook、启动训练或使用 GPU。

## 本轮交付与上轮区别

上轮 `grounded_evidence` 只能提取字面字段，并保留全部原文。本轮新增 `semantic_events_v1`：模型输出具有业务含义的事件，程序负责验证出处与引用，计算当前状态。**相同意思的不同原文可以得到相同 key**，不再要求整个对话字符串相等。

- `tau3_grpo/models/semantic_extractor.py`：异步 `SemanticModel.extract(request)` 接口与 `FixtureSemanticModel`。模拟输出只按完整输入前缀 hash 查询，不看 pair 标签或奖励；缺少模拟响应直接报错，不造空状态。
- `configs/prompts/semantic_events_v1.txt`：完整抽取约定、枚举、字段、证据格式、语义规范化规则及不确定处理。
- `tau3_grpo/algorithms/anchors/semantic_state.py`：来源与结构校验、事件更新、当前状态编码、原采样组隔离。
- `tau3_grpo/analysis/audit_semantic_model.py`：跑模型替身、归并检查和显式的模拟奖励数值探针。
- `configs/analysis/semantic_model_mock_20260914.yaml`：独立配置开关，只允许 `provider: fixture`；不能据此启动真实服务或切换 RL 锚点。

## 怎样表示目标和条件

|事件|表示内容|状态更新约束|
|---|---|---|
|goal|操作、对象、已知参数|区分 add / replace / reaffirm；替换必须引用旧目标，重申不得改变目标|
|constraint|目标范围、谓词、要求/偏好、有效/撤回/满足|不得把一个目标的条件套到另一个目标；撤回/满足必须引用同一旧条件|
|proposal|完整操作列表、每项对应目标、报价和支付角色|新方案明确替代旧方案；重叠方案不能漏报替代关系|
|consent|方案引用、操作下标集合、批准/拒绝/暂停/撤回/有条件|只更新选定操作的批准状态，不将部分批准扩成整个方案|
|question|当前问题及关联方案|改变下一句简短 Yes 的指代|
|context / unknown|保留的原文 / 尚未解释的业务含义|前者进入精确保护字段，后者拒绝比较|

用户只明确说“修改预订”时，未知舱位仍未知，不能根据任务文件填成 business→economy。退款卡与收费卡是不同字段；助手说过的错误报价仍按原样保留，不用重新计算的数值替代。

局部事件 ID、原文位置不进入语义 key；金额小数形式和货币大小写规范化。环境任务、DB、policy、已读事实与工具事件、可选剩余行动预算仍进入 key。`scope_candidate_key` 进一步绑定原始 episode group，防止不同采样组串用步级优势。

## 确认范围如何更新

1. **方案版本绑定**：批准引用完整方案内容。金额、卡、对象或操作范围变更后，受影响的旧批准失效；旧财务承诺保留在历史保护中。
2. **部分批准**：一个方案含“改日期”和“加行李”，批准前者只更新 operation 0。随后明确批准 operation 1，可以累计为相同的完整批准状态。
3. **部分撤回**：撤回行李批准时，日期变更的批准继续保留。
4. **条件按操作生效**：仅约束行李的免手续费条件，不把日期变更的批准一起变成有条件批准。偏好与硬条件分开。
5. **简短回复必须明确指向**：reply 只允许紧邻对应方案/确认问题。插入“用户 ID 是什么”后再说 Yes，不能归给旧取消方案。
6. **条件变化需要重新确认**：新条件或旧条件撤回不会自动继承原批准；同一用户消息里的“yes，但只有无手续费才执行”则可绑定为有条件批准。
7. **任务变化保留旧承诺**：替换目标时，即使旧报价尚未批准，也保留已沟通过的财务方案。

这些状态描述用于比较，不是工具执行授权模块。

## 证据校验能保证什么

事件按消息顺序处理，引用不能指向未来。每个用户/助手消息的非空白字符都必须有事件证据覆盖；只有已知开场问候可忽略，不能随意把业务条件标为“无关”。

文本证据使用原始字符串的字符位置及精确引用；工具证据使用返回位置、JSON Pointer 和原始值，必须能对应到已观察到的成功读取。目标与批准仍必须有当前用户文本，工具返回本身不能创造授权。显式 `quoted_refund/quoted_charge` 必须有被引用的助手金额陈述，不能拿工具计算结果替换。

**机械证据校验不等于语义蕴含判断。** 模型仍可能引用了完整一句话，却误解“只取消其中一个”、错误分配条件范围，或将一次补充误判为替换。模拟模型假设这层理解正确；真实模型接入后必须另测这些错误。

## 模拟验证结果

- 51 个上下文案例，42 个不同前缀的预编写模拟输出。
- 48 个案例生成候选 key；3 个因模糊 Yes、旧方案批准或未解决条件而按预期弃权。
- 34 对归并检查全部符合预期：**11 对合并、20 对分开、3 对弃权**。
- 复用了旧审阅集中的 14 对自然/控制前缀，并新增方案、条件、部分批准和目标变化场景。它们是人工编写的模型替身输出与程序契约检查，**不是新的独立留出集，也不是模型准确率 100%**。
- CPU 回归 **310 passed，2 个第三方弃用 warning**。其中 32 项新增测试覆盖本轮接口、状态转换、来源验证及真正的 GiGPO 数值函数。

原始模拟输入和输出分别保存在：

- `tests/fixtures/semantic_model_cases_20260914.json`
- `tests/fixtures/semantic_model_responses_20260914.json`

它们按字面存储，便于检查“假设模型究竟理解出了什么”，不会在运行时根据预期 pair 标签生成语义。

### 真实 GiGPO 函数的模拟奖励检查

采用两个单动作轨迹，默认 episode + step 权重，均值中心化；以下回报是人为指定的模拟数据：

|场景|模拟终局回报|组合优势|含义|
|---|---|---|---|
|同义状态、同一组|1 / 0|+1 / −1|轨迹级 ±0.5，额外步级 ±0.5|
|报价不同、同一组|1 / 0|+0.5 / −0.5|不能组成同状态组，只剩轨迹级优势|
|同义状态、同一组|1 / 1|0 / 0|没有相对回报差异，不制造信用信号|
|同义状态、不同组|1 / 0|0 / 0|此探针每组只有一个样本；轨迹级和步级都不能跨组比较|

因此，本轮确实打通了“语义归并后产生额外步级优势”的程序路径；**没有证明真实 rollout 中会出现足够多这种组，也没有证明 GiGPO 优于 GRPO**。

## 运行

在 `code` 目录运行，输出目录须为新路径：

```bash
CUDA_VISIBLE_DEVICES='' PYTHONPATH=.:verl:tau2-bench/src TAU3_GRPO_TEXT_ONLY=1 \
.venv-cpu/bin/python -m tau3_grpo.analysis.audit_semantic_model \
  --config configs/analysis/semantic_model_mock_20260914.yaml \
  --output results/analysis/semantic_model_mock_20260914/new_run
```

[版本化验证记录](semantic_model_mock_verification_20260914.json)包含 34 对检查、4 个数值探针、源码/输入 hash 与测试结果。

## 当前可交付结论

在用户指定的“已有正确语义模型”假设下，目标、条件、方案版本与确认范围的归并后端及数值链路已实现并通过上述测试。模拟输出不是可泛化的真实抽取器，代码也没有悄悄替换当前训练锚点。

后续换入实际模型时，可复用同一接口和后端，但还需要对真实完整前缀独立标注并检测语义漏项/误解、状态误合并/过度拆分、有效匹配覆盖率及抽取延迟。机械证据有效、模型自称完成或这批模拟测试通过，都不能代替这项验证。此轮按要求止于模拟接口与后端，不启动真实模型或 RL。
