## 配置与入口

- `training/rl/runtime_defaults.py` 是兼容参数适配器，只读 YAML 和环境，不导入训练框架、不启动服务。基础参数读取已有 `configs/train/rl/base.yaml` 的 rollout/optim/schedule/resources/data；其他兼容默认集中在其 `runtime.environment`。
- Qwen3.5 的诊断默认和模型接线参数移到 `configs/runtime/rl_qwen35.yaml`；`qwen35_full.yaml` 复用环境默认，再覆盖该 profile 的差异。9B 的 4096 MiB 权重传输桶保留。
- `configuration.resolve_arm` 统一解析 arm 与 ablation；启动器和直接 shell 入口共用它。旧 `TAU3_GRPO_CONFIG_*` 覆盖仍生效。
- `run_base.sh` 从 238 行减到 206 行，`run_qwen35.sh` 从 67 行减到 31 行。基础 shell 仍负责路径、预检和 veRL 参数接线，不宣称已变成一行入口；没有为了行数搬走必要的兼容逻辑。
- 启动快照增加 `runtime_configuration_sources` 及 SHA256。它仍是启动输入，不能替代 runner 保存的完整 `resolved-hydra.yaml`。

优先级保持：一般入口使用继承环境覆盖 profile 默认；正式 runner 先显式应用 formal profile，再应用 controller 参数；兼容层只在空值／未设置时补默认（保留 shell 的 `${VAR:-default}` 语义）；原生 Hydra 覆盖最后追加。shell 接收值用 `shlex.quote` 转义，继承字符串不能变成可执行 shell 文本。

`base.yaml` 的 16×8、40-step 是旧直接入口的兼容协议；正式 8×8、20-step 继续以 `protocols/formal50.yaml` 为准。不同协议的显式值不是要删掉的重复，也不能把旧协议全局替换成正式协议而改变历史命令。

## 实验与错误文档

新工具 `python -m tau3_grpo.experiments.review` 支持三种明确回执：GPU 验收汇总、正式 runner 的 controller-state、独立评测 summary。输出 `experiment.draft.md`、`errors.draft.md` 和 `sources.json`，含来源路径、内容 SHA256、原始状态及限定字段。

```bash
python -m tau3_grpo.experiments.review \
  --receipt gpu_acceptance=results/runs/architecture_gpu_acceptance/20260919_s42/final-summary.json \
  --experiment-id architecture_gpu_acceptance \
  --run-id 20260919_s42 \
  --output-dir results/maintenance/review-NEW-UNIQUE-ID
```

独立评测用 `--receipt evaluation=/path/to/summary.json`；正式控制器用 `--receipt formal_controller=/path/to/controller-state.json`。可以多次指定 `--receipt`，每次使用新的输出目录。

工具保留 partial/budget-stop 与 raw failed，不推断“算法失败”或“有提升”。独立评测核对已完成、异常、缺失与计划分母；不完整评测拒绝携带总指标。它只转录回执，没有重新审计原始 trial、加载 checkpoint 或回读云端。未知格式拒绝，任意环境配置和自由错误日志不进入草稿。

人工审阅后把结论纳入现有 `EXPERIMENTS.md` / `ERRORS.md`；工具不自动改索引，不覆盖旧草稿或人工批注。9 月 19 日真实 GPU 汇总已生成一份示例草稿，源 JSON 保持原样。

## 剩余边界

本批收尾不包括强类型配置系统、删除仍有依赖的兼容脚本、行为 logprob/完整采样身份、统一执行有效性策略、全模型同步审计和全面 harness 差分。它们需要各自的行为版本与验证，不宜和目录清理捆成一次变更。通用评测队列、DPPO 和全异步仍为按需求开展的独立项。

后续 GPU 仍需新预算。实测完整 checkpoint 约 50.64 GiB，持久盘当前空闲约 140.65 GiB。按旧控制器每组开始至少 110 GiB 的旋转余量，新增一组后剩余空间就可能低于下一组门槛；不能一次性承诺剩余三组都可执行，也不能擅自删除旧完整 checkpoint。

建议下一段只验收 GiGPO：2 step、128 条候选、4 张策略卡 + 1 张模拟器卡，墙钟硬上限 90 分钟、5 卡预留上界 7.5 GPU-hours。依据前次约 15 分钟策略冷启动、约 38/20 分钟两步耗时，加启动和收尾余量；这是上限，不保证完成。使用新尝试身份引用已通过 A 的证据，不重跑 A/GRPO、不修改旧失败回执、不自动继续 MT/C/D。配置、空间或数值检查失败即停；不够完成下一边界时收尾，到硬上限停止自有进程并保留部分状态。剩余 MT/C/D 应按实际空间和该段耗时再逐段决定。
