|运行|成功|成功占候选|完成官方评分但失败|未完成官方评分|轮数上限|上下文上限|未评分占零分|

所有已评分轨迹的终止原因都是 `user_stop`；所有预算终止轨迹保存的训练 fallback 都是0。**未评分占零分 = 未评分数 / (1,280−成功数)**，不能将其解释为全体任务错误率。

这意味着下一步应同时跟踪“能否在预算内结束”和“结束后结果是否正确”。直接加大 token/轮数预算会改变训练成本和历史对照条件，应另立配置，不在本次顺手调整。

历史 `failure_category` 中的 `tool_errors` 是规则分类，不证明该工具错误就是失败原因；`agent_error` 在这些记录中对应上下文超限，不能据此推断服务故障。重复工具调用也可能用于必要复查，本报告不自动将其判成循环。

这6,400条旧记录都没有新增的 `trajectory_facts_json`。本次只对已有字段做统计，不能宣称补齐了历史 token、逐调用事实或概率重算。

证据：`historical.json`（含100份远程源文件SHA256与逐条摘要）、`historical-summary.json`、`collect_historical.py`。

## 3. 官方 reward 的覆盖边界

train50和selection60的110个任务，经官方 Task 模型解析后均为 `DB,COMMUNICATE`；COMMUNICATE要求为空，也没有额外自然语言或环境断言。参考动作均可执行且无工具错误。

有6个任务的参考动作执行后，数据库与初始数据库完全相同：

|集合|任务|数量|
|---|---|---:|
|train50|airline_174、airline_892|2/50|
|selection60|airline_33、airline_852、airline_802、airline_64|4/60|

对每题构造“仅一条助手文本、没有工具调用、正常agent_stop”的合成诊断轨迹，调用**实际官方 evaluator**，六题均返回reward=1。这是针对评测规范的反例探针，不是模型实际生成结果，也不是声称这些题的所有真实通过轨迹都无效。

当前评分能证明与参考数据库结果一致，但对上述任务不能单凭1分认证信息查询、正确答复、转人工、用户授权或政策遵循已经完成。对需要写库的任务，数据库一致也不能全面认证授权过程与回复文本。

例如airline_174的参考路径包含查询订单和转人工，但探针不执行这两步仍得1分。另一方面，airline_802虽然包含一次参考乘客更新，实际更新是幂等的、没有改变DB。因此这里按**实际参考DB变化**分层，不能仅根据有没有写工具分类。

处理原则：保留官方成绩和原任务集；另列“参考执行不改变DB”分层、过程合规与事实正确性诊断。后续如果增加机器判定条件，先核对任务要求与合法替代路径，单独版本化，不覆盖官方reward或历史结论。不能直接删除这六题后将新分母成绩冒充原协议。

证据：`gold-and-noop-probes.json`。此问题登记为评测规范覆盖风险，与旧“predicted/gold共用可变DB”实现错误区分。

## 4. 过程奖励应怎样解读

历史MT-v3的1,280条中，455条成功轨迹获得过正过程奖励；另243条最终未成功但获得过正过程奖励，其中124条是已评分失败、119条是预算终止。已评分失败中25条用满正奖励预算，预算终止中1条用满。同期记录1,396次工具错误和170次重复参考调用。

这些数量是观测关系。`reference_write/v3`有意取消终局成功门控，所以“部分参考写入正确、任务其余部分失败”可以同时存在。正过程奖励不能作为独立成功率，也不能据此证明发生奖励作弊。后续逐案例区分：确有局部进展、漏做剩余写入、多做或错误写入、以及只完成DB但对话未在预算内结束。

下一轮奖励诊断至少同时输出：正过程/终局成功四格表、按任务分层的关联、重复获奖数、正奖励预算、错误次数，以及完整终局结果。只看跨任务的总体相关性容易被任务难度和参考动作数量混淆。

工作区同期新增的[split候选固定配方诊断](../mt_gtpo_engineering_reward_diagnosis_20260920.md)另行分析反事实奖励与Hybrid优势；本报告不重复计为本次完成的计算。该报告登记的ERR-019针对split候选的GENERIC/DB_WRITE分类，与本报告检查的实际reference_write/v3奖励不同。新候选的诊断不能替换实际训练配方身份，也不能直接证明新策略收益。

## 5. 数据隔离通过了什么，还缺什么

- train50、train200、selection60任务ID均唯一，保存的task hash有效；train50是train200的子集。
- train50与selection60的任务ID、task hash及规范化意图精确检查均无重叠发现。
- 两者全部任务使用相同的四套数据库模板；3,000个train-selection任务对中，391对至少共享一个参考动作实体ID。
- SFT train45/validation5与selection60的来电原因精确重叠均为0；SFT训练/验证对话hash交集为0。这不是完整语义去污染认证。

人工复核文本相似度最高的三对：403/755是相似改签模板但路线与约束不同；159/393共享很强的订票模板但用户/路线/行李不同；1117/548共享用户、订单与付款卡，但任务目标不同。词面相似度只是复核线索，不直接作为泄漏判定。

因此selection60应称为**同工具、同数据库模板下的任务留出评测**。没有发现精确任务泄漏，但不能称为数据库隔离、实体隔离或新环境泛化；没有完成全部任务对的语义去重。本轮未打开final50，不以最终测试集指导奖励调整。

如果后续要声称新环境泛化，应另外设计不与现有库/实体重叠的研究评测集，保留现有selection协议用于纵向对比，并审计SFT来源。新划分不能反向污染final50。

证据：`data-isolation.json`、`data-neighbor-review.md`。

### 首轮差异与harness复验

第一次直接将序列化后的`arguments`送入裸环境，63条轨迹共113次observation不同，另1个中间DB字段为null。原始结果保留，不覆盖为全绿。原因经源码和实际复验定位为：

1. **109次参数校验错误、2次unexpected-keyword错误**：事实JSON使用`sort_keys=True`，重新读取的字典顺序与执行时不同。虽然参数语义相同，Python/Pydantic错误文本里的参数展示或首先报出的多余参数会改变。使用同时保存的`raw_arguments`恢复原始顺序，逐调用返回完全相同；本地版本为Pydantic2.13.5/pydantic-core2.46.5。这说明精确重放不能丢掉raw字段。
2. **2次search_onestop_flight返回**：裸工具产生76,736字符，实际resolved config设置65,536字符、middle截断，模型可见文本为65,553字符（包含截断标记）。应用原harness裁剪后完全相同。它们是实际信息被截断的案例，可能影响决策，但本次没有建立失败因果；不能把“参考动作通常不超限”推广为“所有模型调用都无截断”。
3. **1次未知print_response调用**：失败轨迹`fbcf2b08c5a44f3d9324bc0e1b4fd0ea`，airline_739、DF on step2、turn_index5。dispatch失败路径返回error但没有db_hash字段，记录为null；实际环境重放没有DB变化，后续与最终hash一致。这是观测回执缺失，不是发现了数据库污染。后续可为失败分发补记录当前DB hash与dispatch分类，需新版本测试，不补写历史记录。

对所有63条异常轨迹，使用原始参数、当时resolved config和相同工具执行顺序再次重放，**剩余observation/error差异均为0**。这次验证重建了相应harness转换规则，没有运行完整训练和评测双循环的差分测试；后者留在第二步。

证据：`trajectory-replay.json`、`replay-differences.json`、`harness-followup.json`、`independent-regrade.json`、`provenance.json`；首轮脚本/日志与跟进脚本/日志全部保留。

## 7. 下一阶段的具体优先级

1. 先将当前结论形成固定诊断切片：官方成功、已评分失败、预算终止、无DB变化参考任务、正过程但未成功。历史主指标不变。

## 8. 复核与复现

本次脚本是一次性离线分析，保存在忽略的results目录，不新增生产入口。`audit.py`禁止网络连接，使用独立内存环境重放；启动时LiteLLM尝试读取公共价格表被拦截，随后使用本地备份，没有发生模型/API推理。

脚本采用排他创建输出，避免覆盖证据。要复现应将脚本复制到新的同层 `results/analysis/<新审计ID>/`，不要直接在已完成目录重跑：

```bash

  .venv-cpu/bin/python results/analysis/<新审计ID>/audit.py
```
