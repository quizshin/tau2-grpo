# GiGPO / MT-GTPO 分批消融计划

状态：正式算法消融仍为计划；第二步工程验收于 2026-09-19 获得有上限的单次授权并已启动，见 [执行记录](gpu_acceptance_20260919.md)。该授权不覆盖第三、四步正式实验。保留现有算法路线，借鉴参考仓库的模块边界、统一评测和成本报告，不复制 DPPO 或迁移 SkyRL。

## 第一步：已有数据与工程验收（CPU）

用同一评分器重算旧独立评测，核对协议、完整性、pass@k/pass^k、百分点变化、按任务配对 CI、工具错误和成本覆盖率。E2 原始评测不完整，保持不可排名；MT-GTPO 训练内 validation 单列。旧数据已被多次检查，所有基于这些材料的奖励/anchor 研究属于开发分析。

先证明结构迁移不影响已有奖励、优势与 mask；检查公开接口、三条 estimator 切换、配置、会话隔离与 checkpoint 记录。不要把多项行为变更叠在第一次 GPU 集成验收里。

## 第二步：已获单次预算授权的 GPU 集成验收

使用独立结果目录，先做最小任务预算的服务与 rollout smoke，再做小批次非零更新及保存/恢复。三个 estimator 逐一验证；GTPO DF 至少覆盖开/关。该短程流程必须显式声明保存频率例外，不放入正式对照排名。本次卡数、时间和候选上限见执行记录；阶段是否通过以机器回执为准。

## 第三步：匹配预算的算法主对照

|组|目的|变化|
|---|---|---|
|SFT|共同推理起点|不做 RL|
|GRPO / GRPO+DF|终局优势与组过滤基线|仅 DF 开关|
|GiGPO / GiGPO+DF|episode + step 信用分配|同一 anchor 版本，仅 DF 开关|
|MT-GTPO / MT-GTPO+DF|终局 + 过程混合信用分配|同一通过验证的 reward recipe，仅 DF 开关|

正式默认 train50、seed42、20×64=1,280 条候选，学习率/KL/模型/模拟器/调度/precision/上限均匹配 AGENTS。记录实际更新次数与有效组/token；固定候选预算不等于固定有效训练量或 GPU 成本。paper_env_split_v3 尚无新数据验证，不因历史相关性较高直接作为正式胜者。

## 第四步：定位有效机制

GiGPO：先做 step 系数 0 的 episode-only 对照，再与明确版本的规则 anchor 比较；最小组数/归一化/组 UID 作用域逐项改变。语义 anchor 必须先通过独立的可见状态与误合并审计，不能默认在线启用。

MT-GTPO：终局-only、终局+执行错误、终局+参考写入、完整候选 shaping 分开；过程权重、混合系数、轨迹内归一化、联合优势之后的 DF 各自单项消融。具体开关先确认实现到达实际 estimator，再登记为可运行组；本表不承诺所有组合已接通。奖励可靠性与信用分配收益分两步验证。

Harness：原始终止原因、跨算法统一轮次事实记录、响应/token 预算、训练与独立评测协议差分单独验收。修复 stop/length 分类或改变终止策略可能改变轨迹分布，不能混进纯目录迁移。DPPO、prompt-group loss reduction 等仅在已有基线清楚后作为独立研究。

## 指标与判读

主指标 pass@1；辅助 pass@2/4、pass^2/4。按共同任务给出 Δpp、相对变化及 task bootstrap CI；候选确定后至少多个训练 seed 才讨论稳定收益，先与用户确认总预算。补充工具错误率、轮数、终止分布、输入/输出 tokens、有效组、优势密度、KL、梯度、过滤率、候选与更新吞吐、峰值显存、wall time/GPU-hours。

按同样完整评测计划比较，不能用训练 reward 代替成功率。机制审计的“组重复/奖励密集/相关性升高”只是信号证据，不等于模型改进。最终模型和协议确定后再使用 final50；此前所有调优只按登记的数据用途进行。
