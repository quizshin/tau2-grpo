旧数据确有较多完整多动作轨迹，不能说项目没有任何复杂流程素材；但动作数量不是内在难度，存在多个动作也不证明目标、政策、费用及收尾正确。149版本68条多动作说明值得复核复用，并不能跳过来源与语义门槛。

开场行为也存在明显分布差异：旧100中98条首工具为 profile；repair72中63条首工具为订单、3条profile、3条联程搜索、3条机场查询。两种模式各有适用场景，课程应按信息需求覆盖条件分支，不能强制统一开场动作。

1. **合并审核证据，不合并训练文件。** 以 source ID + 内容哈希去重，归并旧train100/dev52、109条后续接受记录、40条hold、repair72/22、40+14衍生数据和23题候选的证据。记录历史梯度曝光、离线dev曝光、实体、源任务/DB、语义家族、工具执行与语义审核状态。repair72与旧衍生40来自相关构造链，不能简单相加当112条独立新样本；相同来源、同实体和模板家族需单列。
2. **完成分组与难度标注。** 接续 `results/analysis/sft_prefix_audit_20260926/curriculum_label_queue.jsonl`，152条当前均为 `label_status=pending`、`group_status=pending_semantic_family_review`。保留旧难度仅作历史字段；按实际目标、约束耦合、状态依赖、恢复/重规划证据标注。新候选加入同一字段规范，未知保留unknown。
3. **先补完整流程缺口。** 承接23题参考回放与5题初审；优先建立改签后行李额度重算、多订单取消且保留无关订单、乘客修改后续依赖、合法拒绝后继续其他子目标、工具失败恢复以及真实完成后收尾。复用 `grounded_gap_pilot.py`、`grounded_repair.py`、`decision_repair.py` 的真实工具/独立终态检查机制，在现有职责内扩展，而非新建平行生成系统。当前没有新增完整训练轨迹。
4. **先冻结家族隔离再派生变体。** 旧dev52、repair dev22、新能力dev14的历史归属均保留，合并保护实体/家族元数据；有曝光冲突就记录并隔离，不能把训练过的数据搬进“未见dev”。实体隔离不等于模板家族独立。已有23题的保护筛查基于117用户，不自动保证覆盖未来新增保护集合。
5. **复用 `tau3_grpo/data/curriculum_split.py`。** 完成 `group_status=reviewed`、`label_status=reviewed`、`difficulty_basis=task_constraints` 与两个依赖布尔字段后，按固定seed42生成新候选manifest。代码只负责划分，必须先通过独立质量纳入门槛；它不会自动裁定原始样本可训练。保持旧历史split锁和protected groups，不为凑10%拆家族。
6. **物化真正累积课程。** A=合格foundation；B=A+合格constraints；C=B+合格strategy。目标上限仍可为100/250/400，但按实际合格量报告，不强凑数量。保留完整对话与明确assistant监督位置；记录各阶段新增/累计来源、历史重复暴露、监督token、预计更新次数。阶段数量、LR和epoch要与当前实现核对后冻结，不能把旧计划参数当已批准的新实验。
7. **以交互表现验收。** 离线loss仅检查拟合；需要按桶及适用分母看完整任务成功、严重政策错误、重复停滞、预算终止与准确收尾。阶段SFT将来与固定repair_base起点作同协议对照；不直接混用60×1与历史60×4分数。不把主线RL已用任务或模板变体宣称为完全独立SFT确认集。

当前无需为数据盘点另开GPU。后续API/GPU需求另列目的、规模、预算和授权；本次审计新增API调用0、GPU小时0。
