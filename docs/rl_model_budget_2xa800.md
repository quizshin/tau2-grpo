# 两张 A800 80 GiB：Qwen3.5 RL 模型选择

预算日期：2026-09-08。服务器为 2×A800 80 GiB PCIe；容器内存额度
240 GiB、CPU 28 核。下列是模型配置计算值和部署预算，不是 4B/9B GPU 峰值实测。

对照设计建议使用 **Qwen3.5-4B 策略**，在相同 SFT checkpoint 上分别做
全量 RL 和 rank-16 LoRA RL。另做 9B LoRA 作为容量扩展。
不能用 4B 全量与 9B LoRA 的差异直接证明某种微调方法更好。

用户选择的 **Qwen3.8-27B INT4 模拟器**已通过单卡推理验证，见
[模拟器配置](qwen38_simulator.md)。下面 16–20 GiB 的模拟器预算只适用于
原 4B 模拟器，不能直接用于 27B。27B 量化权重文件本身约 19.6 GiB，
还需要运行时内存与缓存。两卡全量 RL 与此模拟器的组合尚未验证可运行，
0.8B 策略 + 4B 模拟器已完成下文的三步执行链路验证。

## 静态状态预算

通过本地 Qwen3.5 配置在 meta device 上建立模型并统计真实参数，不加载权重。
全量统计全部语言参数（含 embedding、LM head）；视觉部分冻结。
全量使用 FP32 参数/梯度/Adam 一、二阶状态（语言参数每个 16 bytes）；LoRA
使用 BF16 冻结基座与 FP32 adapter 训练状态。均不含激活、临时张量、推理缓存。

| 策略 | 语言参数量 | rank-16 adapter 参数 | 全量静态状态 | LoRA 静态状态 |
|---|---:|---:|---:|---:|
| Qwen3.5-4B | 4,205,751,296 | 32,464,896 | 63.91 GiB | 8.94 GiB |
| Qwen3.5-9B | 8,953,803,264 | 43,278,336 | 135.12 GiB | 18.17 GiB |

4B、9B 纯语言 BF16 推理权重分别约 7.83、16.68 GiB。
这两个配置的注意力 KV 缓存，在单条 16,384-token 序列下均约 0.5 GiB，
还需要另计 Gated DeltaNet 状态、workspace 和运行时开销。
24,576-token 完整 BF16 logits 约 11.37 GiB；反向传播和 log-softmax 会增加临时内存。
因此不能只用“参数量乘 2 bytes”估计 RL 显存。

## 原 4B 模拟器的候选部署

- **4B 全量 + 4B 模拟器：主方案。** 策略使用两卡 FSDP 分片；rollout 可用
  TP=2。模拟器与 GPU 1 共享显存，先限制在约 16–20 GiB，而不是独占其 80 GiB。
  每张卡的全量静态训练状态约 32 GiB；训练阶段释放 rollout KV 缓存，并控制
  reference 驻留、激活检查点和 micro-batch。24k 长度的峰值需实际验证，不能保证
  保留完整大词表 logits 的未优化路径一定可装下。
- **4B LoRA + 4B 模拟器：公平对照组。** 与全量组共享同一 SFT 起点、数据、
  模拟器、上下文上限、rollout 预算。显存节省用于并发与吞吐，不改变有效训练预算。
- **9B LoRA + 4B 模拟器：容量扩展方案。** 优先验证 GPU 0 策略/rollout、GPU 1
  模拟器；如果长上下文或并发需要，再改为两卡策略并与模拟器共享 GPU 1。
- **9B 全量 + 4B 模拟器：暂不作为首选。** FP32 Adam 路径静态状态已约
  135 GiB，分片后每卡约 67.6 GiB，余量不足以稳妥容纳长对话和模拟器。
  若必须做，应另验 FSDP2 CPUOffloadPolicy 或增加 GPU/外置模拟器。

当前 legacy FSDP 的 `optimizer_offload=true` 会在 actor update 前把 optimizer
状态搬回 GPU，不能当作真正的 CPU optimizer、也不能直接据此声称 9B 全量能装下。
FSDP2 的 `offload_policy` 是另一条实现，仍需验证梯度累计、保存与 rollout 权重同步。

正式初始预算建议 16 个任务 × 每任务 8 条 rollout = 128 条/更新；从较低并发开始，
根据 tokens/s、trajectories/hour 和更新峰值调整到 32/64 并发。保留每卡至少约
8–12 GiB 的瞬时分配余量；不同阶段会释放和重用显存，不能要求全程固定占满 160 GiB。

换成 4B 或 9B 需要从对应基础模型重新做 SFT；0.8B SFT/adapter 不能跨尺寸复用。

## 2026-09-08 三步验证结果

修复 FSDP 冻结共享 embedding 后，0.8B LoRA + 4B 模拟器完整执行 3 步、
24 条真实轨迹，退出码为 0；保存和权重同步流程通过，保留 checkpoint 2/3。
24 条官方 reward、GRPO advantage 和三步梯度均为 0，adapter SHA-256 未变。
这是执行链路验收，尚未证明有有效学习或非零 adapter 更新后的同步正确性。

本轮 nvidia-smi 峰值：GPU 0 为 65,157 MiB（63.63 GiB），GPU 1 为
49,233 MiB（48.08 GiB）；actor Torch allocated / reserved 峰值分别为
58.57 / 62.01 GiB。三步耗时 26 分 05 秒，每次 actor 更新约 266–268 秒。
输入固定为 `[8, 24576]`，有效上下文只有 4,658–8,396 tokens；大量 padding
仍经过原生 Gated DeltaNet 和 LM head。现有路径显存/计算开销主要受这些
长序列临时张量影响，不能按参数量线性外推 4B/9B 峰值。下一步应验证保留
全部有效上下文的 padding 裁剪、选择性 LM head 和快速 kernel，再上大模型。

Qwen3.8-27B INT4 模拟器已通过单卡加载和三轮对话检查，模型加载 18.23 GiB；
0.65 vLLM 预算服务占用快照约 51.58 GiB。8 并发、16 个短 Airline 输入热缓存
测试为约 170.8 输出 tokens/s，详见模拟器文档。全量 RL 共置时仍需降低模拟器
缓存预算并单独验证；不能将此配置与两卡 FSDP 直接叠加。

对于 4B 全量 + 27B INT4 模拟器，更适合验证按阶段复用两卡：采样阶段将
actor 训练状态卸载，运行策略 rollout 和模拟器；更新阶段让两路推理服务
释放 GPU 权重/缓存，再进行两卡 FSDP 更新。外部模拟器的 sleep/wake 协调
尚未接入本项目，这只是后续待验证方案，不能直接用现有 launcher 宣称支持。
若保持模拟器始终驻留，就需要另测更低缓存预算、真正的 CPU optimizer，
或把模拟器放到其他机器。目标应是提高有效轨迹与更新吞吐，保留必要的
瞬时分配余量，不能把 nvidia-smi 全程占满当作训练效率的证明。

## 2026-09-09 更新：4B LoRA + 27B INT4 模拟器

以下为开跑前预算判断；本日稍后完成的 RL-009 实测见本节末尾。两张 A800 均为 81,920 MiB，预算检查时占用为 0。建议先验证 GPU0 独立放
Qwen3.5-4B LoRA actor/rollout、GPU1 独立放 Qwen3.8-27B-AWQ-INT4 用户模拟器。
这是有条件可行的候选配置，尚无该组合完整 RL 更新的实测，不能称为已跑通。

| GPU | 工作 | 预算依据 |
|---|---|---|
| 0 | 4B BF16 冻结基座 + r16/alpha32 LoRA；TP1 rollout | actor 静态状态约 8.94 GiB；不含激活、logits、rollout 权重及缓存 |
| 1 | 27B INT4 用户模拟器，16k 上下文，关闭 thinking | 0.65 vLLM 预算约 52 GiB；历史占用快照 51.58 GiB，非满长度峰值 |

LoRA 的 reference 概率由关闭 adapter 的 actor 计算，不应简单重复预算一整份
常驻 reference 权重；rollout 的模型及缓存仍需独立计入不同阶段的显存。
首轮可用 micro-batch=1、梯度检查点、4 条 rollout 并发、每任务 group size=4；
并发数与总轨迹预算分开设置。actor 状态 offload 只在阶段间省显存，更新时
仍需搬回 GPU。模拟器独占 GPU1 时，没有必要为了 GPU0 的 OOM 减少模拟器缓存；
两张卡的空闲显存不会自动合并。

24,576 长度的 BF16 完整 logits 本身约 11.37 GiB。今天的分块修复只降低
无梯度 log-softmax 临时开销，未改变反向传播路径，也未消除完整 logits。
0.8B LoRA 在相同 24k padded 路径的整卡峰值已达 65,155 MiB，不能据静态
状态为 4B 断言某个整卡峰值。若保持原 24k 有效上下文预算，优先验证只裁剪
padding、减少无用 LM-head/logits 的实现；不能直接打开现有不安全的通用
packing，也不能把缩短上下文后的通过冒充原协议通过。

验收应先跑单批完整的 rollout → old/ref log-prob → backward/update →
权重同步 → 下一批 rollout，并测量实际长样本；目标至少保留约 8 GiB
显存余量，该数字是部署目标，不是实测保证。此步骤通过后再扩大实验预算。
若单卡策略仍不够，需要另做两卡共享/分阶段资源协调，现有 launcher 尚未
证明该路径可用。

沿用 SFT → RL 主线时，需要先训练对应 4B SFT；当前已核实的本轮 SFT 成品
是 0.8B，不能跨尺寸复用。可用原始 4B 做纯工程探针，但须单独标记起点。
本轮改变了策略规模和模拟器，结果不能与 0.8B + 4B 的奖励直接归因比较。

当前数据盘约剩 15 GiB，持久盘约剩 120 GiB。27B 五片权重已有持久副本，
直接从 `/root/autodl-fs/tau3_grpo_fix/model_store/Qwen3.8-27B-AWQ-INT4` 加载，
不复制到数据盘；新检查点直接写持久盘，并预算新旧两份同时存在。
专用环境入口为 `/root/autodl-fs/tau3_grpo_fix/runtime/venvs/qwen38-sim/bin/python`；
旧 `/root/tau3-staging/qwen38` 路径当前已不存在。以上文件存在性已确认，
没有在此次预算检查中重新计算全部大型模型 hash 或启动新训练。

### RL-009 完成后的实测更新

4B LoRA SFT已完成30步，最佳验证loss 0.354217，第24步恢复后合并作为RL起点。
GPU0的4B LoRA策略与GPU1的27B INT4模拟器已在24576上下文预算下完成3次更新，
每步8条轨迹，整步17.85/22.90/20.30分钟，总61.05分钟；每次actor更新约9.20分钟。
生产路径在既有无梯度log-prob分块之外增加无梯度熵统计分块，autograd路径未改变。

5秒整卡采样峰值GPU0为79,755MiB（77.89GiB），GPU1为51,119MiB（49.92GiB）。
因此该配置已有三步可运行证据，但GPU0仅剩2.11GiB，未达到前述8GiB余量目标。
更高并发或更长有效轨迹仍需实际验证，不能把这次通过推广为任意24k负载保证。
三批成功数6/8、1/8、1/8，三步LoRA数值同步均通过。

只按当前8条/步粗略外推，40/60步的训练循环约13.57/20.35小时，另计启动、评估与保存波动。
这不是128条/步正式预算的耗时：轨迹数增至16倍会显著增加采样和更新工作，
实际优化器步数、任务分布与吞吐须根据正式配置重新估算。本轮没有启动该规模。
结果、限制与证据见[4B LoRA记录](4b_lora_sft_rl_20260909.md)。
