# MT-GTPO 预算截断时的状态审计

2026-09-20。状态：`cpu_verified / diagnostic_only`。307 条截断轨迹、3,319 次实际调用重放完成。本轮只分析旧记录，不修改官方评分、终止原因、奖励配方或训练。

## 要回答的问题

预算结束后官方回退 0，不等于数据库一定未达标。本轮估计的是：**现有截断轨迹中，有多少在截断时已经与参考目标数据库完全一致？** 这不是增加预算后的成功率估计，也不是 value/critic bootstrap；没有生成任何后续对话。

输入为历史 reference_write_v3 的 1,280 条候选中全部 238 条截断，以及 MT-GTPO DF off/on 工程验收 256 条候选中全部 69 条截断。它们来自训练中的不同策略和任务组，不能视为独立同分布样本、新策略评测或盲测。

4 条最终达标均属于 `max_steps`。轮数截断合计 256 条，其中 4 条达标；上下文/累计响应预算截断 51 条，0 条达标。历史对应 194/44 条，工程对应 62/7 条。

这些 4 条占历史全部候选的 2/1,280 = 0.15625%，占工程全部候选的 2/256 = 0.78125%。这是可确认的“状态已达标但提前终止未获 DB 评分”规模；**不是正式成绩增幅，也不是加预算能恢复的成功数上界或下界**。延长预算可能使未达标者完成，也可能让已达标者继续偏离。

所有 4 条任务的参考动作都会改变数据库，并非初始 DB 已经符合参考目标的空操作情况。DB 相等也不证明对话完成、用户授权或策略合规。

307 条中 245 条出现过执行错误，共 1,194 次错误调用；91 条重复过同工具、同参数的错误调用。这是现有记录的描述，不是证明错误导致截断的因果估计。

## 可定位实例

轮次在此使用人类可读的 1-based 编号，产物保持原 0-based `turn_index`。

- 历史 `airline_664`，step4 row55：第 5 轮更新行李后达到目标，之后继续查航班/订单，最终第 15 轮截断。存在较长的达标后交互，不能都解释成只差最后一个工具调用。
- 历史 `airline_369`，step5 row19：第 15 轮完成最后两笔取消，其中第二笔后才达到目标，当轮触及预算。

另有 3 条工程轨迹曾一致后偏离：`airline_739` 取消后达标、随后更新航班而偏离；`airline_574` 订票后达标、随后发放凭证而偏离；`airline_892` 属于初始 DB 即与参考目标相等的特殊任务，之后修改乘客而偏离，不能当作真实完成任务后又做错的等价案例。

## 与错误信用的关联

保持上一轮固定 split v4 权重、分组和优势不变，仅按原 source/row 连接状态结果。历史 230 个“截断且正优势”的错误轮均属于最终未达标轨迹；工程 80 个中只有 2 个属于最终达标轨迹，均来自上述 `airline_574`（原 turn12/13）。其余 78 个最终未达标。

因此，大部分此类正信用不能用“实际早已完成目标，只是官方没评分”解释。但是未达标轨迹也可能包含有用的局部纠正动作，不能由此推导应将全部过程奖励清零或屏蔽全部截断轨迹。

## 实现与验证边界

官方 evaluator 在非 `AGENT_STOP/USER_STOP` 时提前返回 reward=0、reward_basis=None（`tau2-bench/src/tau2/evaluator/evaluator.py:119`）。本审计保留该结果，不伪造正常终止。状态判断沿用 `evaluator_env.py` 的 agent/user DB hash 精确相等逻辑。

各任务独立执行 reference actions 构造目标，每条候选从对应原始 DB 独立重放，只执行已记录为实际执行的调用。任务断言限定本批：无 initial_state、reward_basis 为 DB/COMMUNICATE、communicate/env/nl 附加条件为空。没有推广到别的领域或带额外判据的任务。

执行记录：远程既有环境完成独立目标与全部最终记录的初步比较。远程串行重放较慢；8 进程尝试后查明容器 cgroup 仅 0.5 CPU/2 GiB，出现 OOM worker 退出，已中止并保留日志。后续将 24 份原始输入按 SHA256 核对后复制到本地 `.venv-cpu` 完成重放；本地串行首个尝试为减少重复哈希而中止，日志保留。最终驱动复用上一调用哈希，官方声明不修改状态的工具无需重复计算全 DB；每条终态仍重新计算完整哈希，逐调用已记录的哈希仍逐一比较。实际工具执行没有被跳过。

本轮未启动模型 API、GPU、采样、训练或续训。并行失败不是轨迹失败，不能混入统计分母。

307/307 条最终 DB hash 及执行调用数与原记录一致；3,318 份已保存逐调用 DB hash 全部一致，1 份旧回执缺失（工程 DF on step2 row40、airline_739）继续标记缺失。每次执行的 error flag 与历史一致。24 份原始输入、manifest、所用 DB 文件 SHA256 全部通过；本地/远程 8 个相关源码与指令文件哈希一致。独立 snapshot 与完整重放的 307 条 source/row/state 逐条对齐。

首轮有 162 条轨迹、282 次调用的返回文本不同，全部为参数错误。单独核查完整错误文本：77 次采用保存的 raw 参数顺序后逐字一致；204 次验证错误字段及其余消息相同，只是 Pydantic 的 input_value 字典展示/缩略不同；1 次同一含多个非法参数的调用因顺序不同先报告了另一个非法参数。后 205 次缺历史 raw 顺序，不宣称原文精确复现、不补造顺序。核查过程的数据库未变化，原差异与分类保存在 `observation-check.json`，不会把这些文本差异当作状态验证通过之外的额外成功。

## 对后续处理的建议

1. 官方结果继续保留终止原因、reward 和 scored；旁路记录 `state_at_cutoff`，不要把未评分和已评分失败混成同一诊断类别，也不要把旁路状态判断冒充官方成功。
2. 优先处理工具参数错误、重复尝试和达标后的冗余交互；仅补“完成状态分”覆盖的现有案例很少。167 条有状态变化但未达标，不能一律称为有效进展。
3. 预算消融需另行固定策略、任务和共同样本，测额外预算能恢复多少完成率、消耗多少 token，以及新增偏离。当前数据不能给出“15 轮改 20 轮会提升多少”的可靠数字；本轮没有执行这种实验。
4. 错误局部信用与未来过程信用仍应独立做消融。此次没有改变优势公式、裁剪规则或给所有截断轨迹追加终局奖励。
